# Vision Platform: Complete Database Architecture Design

## Project Context
Vision is a live session learning platform with a red/blue color scheme, prioritizing teachers as the primary users with powerful management tools for conducting online sessions.

## Required Analysis Scope

### 1. Platform Overview Analysis
Based on the three overview files provided (Student, Teacher, Admin), analyze and extract:
- All user roles and their specific requirements
- Core features and functionalities for each role
- Data relationships and dependencies
- Real-time vs persistent data needs
- Access patterns and query requirements

### 2. Database Selection Strategy
For EACH identified data entity/table, provide:

#### PostgreSQL Consideration
- When to use: Explain if this entity needs ACID compliance, complex relationships, transactions
- Schema design: Specific table structure with columns, data types, constraints
- Reasoning: Why PostgreSQL fits (or doesn't fit) for this specific use case
- Indexing strategy: What indexes are needed and why
- Relationships: Foreign keys, joins, normalization level

#### MongoDB Consideration
- When to use: Explain if this entity needs flexibility, nested data, horizontal scaling
- Schema design: Document structure with fields, embedded vs referenced documents
- Reasoning: Why MongoDB fits (or doesn't fit) for this specific use case
- Indexing strategy: What indexes are needed and why
- Data modeling: Embedding vs referencing decisions

#### Redis Caching Strategy
- What to cache: Specific data that needs caching
- Cache patterns: Cache-aside, write-through, or write-behind
- TTL strategy: Expiration times and reasoning
- Key naming convention: How keys should be structured
- Invalidation strategy: When and how to invalidate

### 4. Critical Analysis Points

For EACH design decision, address:

1. **Scalability:** How will this scale with 10K, 100K, 1M users?
2. **Performance:** Query performance expectations and optimizations
3. **Consistency:** ACID requirements vs eventual consistency tolerance
4. **Real-time needs:** WebSocket data, live updates, presence systems
5. **Data size:** Expected growth and storage implications
6. **Query complexity:** Simple lookups vs complex aggregations
7. **Transaction needs:** Multi-document/table transactions required?
8. **Backup/Recovery:** Point-in-time recovery needs
9. **Cost implications:** Storage and compute costs at scale
